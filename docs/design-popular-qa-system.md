# 실시간 인기 질문·답변 집계 & 어드민 대시보드 설계

> **핵심 철학**: 사용자에게 단순히 "많이 묻는 질문"을 보여주는 것이 아니라, **"왜 이 질문이 많이 나오는가"** 를 분석하고 **"AI는 이 문제를 어떻게 바라보고 답했는가"** 를 보여줌으로써 사용자 스스로 깨달음을 얻도록 유도한다. 질문 카드는 바로가기가 아니라 **통찰의 창**이다. 관리자는 이 데이터를 확인하고 질문/답변을 직접 수정할 수 있다.

---

## 1. 핵심 설계 철학: "질문 바로가기" → "통찰의 창"

### 기존 접근 (❌ 폐기)
```
사용자가 인기 질문 카드를 누른다 → chat_input에 질문이 자동 입력된다 → AI가 답변한다
```
이 방식은 **편의성**만 제공할 뿐, 사용자의 이해나 성장에는 기여하지 않는다.

### 새로운 접근 (✅ 채택)
```
사용자가 인기 질문 카드를 누른다
        ↓
   [통찰 패널 열림]
        ↓
   ┌─────────────────────────────────────────┐
   │ 1. 이 질문이 많이 나오는 이유 (근본 원인)    │
   │    → "왜 342명이 같은 고민을 할까?"        │
   │    → 중독 회복자의 공통 심리 분석            │
   ├─────────────────────────────────────────┤
   │ 2. AI는 이 문제를 어떻게 분석했는가         │
   │    → 질문의深层 구조 파악                   │
   │    → 핵심 쟁점과 진짜 필요를 진단            │
   ├─────────────────────────────────────────┤
   │ 3. 실제 도움된 답변과 그 이유               │
   │    → 가장 👍 받은 답변 공개                │
   │    → "왜 이 답변이 도움되었는가" 분석        │
   ├─────────────────────────────────────────┤
   │ 4. 당신을 위한 물음 (깨달음 유도)            │
   │    → "당신은 지금 어디에 있습니까?"          │
   │    → 개인화된 성찰 질문 제시                │
   └─────────────────────────────────────────┘
        ↓
   사용자가 스스로 깨닫고, 원하면 직접 질문
```

### 사용자 여정 설계

```
사용자 방문
    │
    ├─ "나만 이런 고민 하는 게 아니구나" (공감)
    │    └─ 인기 질문 카드: "342명이 같은 질문"
    │
    ├─ "왜这么多人이 이걸 묻지?" (호기심)
    │    └─ 탭 → 원인 분석: "중독 회복의 첫 관문은..."
    │
    ├─ "AI는 어떻게 답했지?" (탐구)
    │    └─ 스크롤 → AI 진단 + 실제 답변
    │
    ├─ "아, 그래서 그렇구나" (깨달음)
    │    └─ 핵심 인사이트 문장 하이라이트
    │
    └─ "그럼 나는?" (행동)
         └─ 개인화된 성찰 질문 → 직접 입력 or 다음 카드
```

## 3. 데이터 모델 설계

### 3.1 기존 테이블 (변경 없음)

```python
# backend/app/models/orm.py — Interaction (기존)
class Interaction(Base):
    __tablename__ = "interaction"
    interaction_id: str      # PK
    subscriber_id: str?      # FK → subscriber
    question: str            # 사용자 질문
    answer: str              # AI 답변
    feedback: int?           # +1(👍) / -1(👎) / null(무응답)
    created_at: datetime     # 생성 시각
```

### 3.2 신규 테이블

#### `qa_trend_snapshot` — 집계 스냅샷 + 통찰 데이터

| 컬럼 | 타입 | 설명 |
|------|------|------|

| `raw_variants` | JSON | 원본 질문 변형 목록 `[{text, count}]` |
| `total_count` | INT | 전체 출현 빈도 |
| `recent_count_7d` | INT | 최근 7일 빈도 |

| `positive_feedback` | INT | 👍 개수 |

| `fb_ratio` | FLOAT | 👍 비율 (0~100) |
| `trend_score` | FLOAT | 통합 트렌드 점수 (가중치 계산) |
| `category` | VARCHAR(40) | 주제 분류 (중독·회복·신앙·관계 등) |
| `computed_at` | DATETIME | 집계 계산 시각 |
| `is_featured` | BOOL | 관리자 수동 피처링 여부 |
| `is_hidden` | BOOL | 관리자 숨김 처리 여부 |
| `admin_edited_text` | TEXT? | 관리자 수정 버전 (null이면 원본) |
| `edited_at` | DATETIME? | 수정 시각 |
| `edited_by` | VARCHAR(40)? | 수정자 |
| 🆕 `root_cause_analysis` | TEXT? | **LLM 생성: 이 질문이 많이 나오는 근본 원인 분석** |
| 🆕 `ai_diagnosis` | TEXT? | **LLM 생성: AI가 이 문제를 어떻게 진단/구조화했는가** |

| 🆕 `best_answer_text` | TEXT? | **가장 👍 받은 답변 본문 (캐시)** |
| 🆕 `best_answer_why` | TEXT? | **LLM 생성: 왜 이 답변이 도움되었는가 분석** |
| 🆕 `reflection_prompt` | TEXT? | **LLM 생성: 사용자에게 던질 성찰 질문** |
| 🆕 `insight_generated_at` | DATETIME? | 통찰 데이터 생성 시각 |
| 🆕 `insight_version` | INT | 통찰 데이터 버전 (재생성 시 증가) |
| 🆕 `review_status_root_cause` | VARCHAR(10)? | `"pending"` \| `"approved"` \| `"rejected"` — 근본원인 검수 상태 |
| 🆕 `review_status_ai_diagnosis` | VARCHAR(10)? | AI 진단 검수 상태 |
| 🆕 `review_status_best_answer_why` | VARCHAR(10)? | 도움된 이유 검수 상태 |
| 🆕 `review_status_reflection` | VARCHAR(10)? | 성찰 질문 검수 상태 |
| 🆕 `last_reviewed_by` | VARCHAR(40)? | 마지막 검수자 |
| 🆕 `last_reviewed_at` | DATETIME? | 마지막 검수 시각 |
| 🆕 `ai_model_used` | VARCHAR(40)? | **🆕 통찰 생성에 사용된 AI 모델** (예: `"gemini-2.5-flash"`, `"deepseek-v4"`) — 모델별 품질 추적용 |
| 🆕 `needs_regeneration` | BOOL | **🆕 재생성 필요 플래그** (주간 배치에서 True인 항목만 재생성) |

| 🆕 `published_at` | DATETIME? | **🆕 사용자에게 최초 공개된 시각** — 모든 섹션 approved 되는 순간 설정 |
| 🆕 `deleted_at` | DATETIME? | **🆕 Soft delete** — 삭제된 스냅샷은 모든 API에서 제외, 복구 가능 |
| 🆕 `insight_prompt_version` | VARCHAR(10)? | **🆕 통찰 생성에 사용된 프롬프트 버전** — 프롬프트 변경 추적용 |

**인덱스**: `(snapshot_type, computed_at DESC)`, `(trend_score DESC)`, `(fb_ratio DESC)`, `(review_status_root_cause)`, `UNIQUE(canonical_text, snapshot_type) WHERE deleted_at IS NULL`

#### `qa_admin_edit_log` — 편집 감사 로그 + 버전 스냅샷

| 컬럼 | 타입 | 설명 |
|------|------|------|
| `log_id` | UUID PK | |
| `snapshot_id` | FK → qa_trend_snapshot | |
| `field` | VARCHAR(20) | `"question"` \| `"answer"` \| `"root_cause"` \| `"ai_diagnosis"` \| `"best_answer_why"` \| `"reflection"` \| `"is_featured"` \| `"is_hidden"` |
| `old_value` | TEXT? | 변경 전 값 (최대 10000자까지 저장, 초과 시 truncated 표시) |
| `new_value` | TEXT? | 변경 후 값 |
| `edit_reason` | VARCHAR(200)? | **🆕 수정 사유** (관리자가 입력, 예: "신학적으로 부정확한 내용 수정") |
| `ai_version` | VARCHAR(20)? | **🆕 AI가 생성한 버전 식별** (예: `"gemini-2.5-flash-v1"`, `"deepseek-v4-v2"`) |
| `diff_summary` | TEXT? | **🆕 변경 사항 요약** (LLM 자동 생성, 예: "3문장 수정, 1문장 추가, '죄책감'→'은혜' 용어 변경") — 관리자 검토용 |
| `edited_by` | VARCHAR(40) | 수정자 |
| `edited_at` | DATETIME | 수정 시각 |
| `reverted` | BOOL | **🆕 롤백 여부** (True면 이전 버전으로 되돌림) |
| 🆕 `old_value_hash` | VARCHAR(64)? | **🆕 old_value의 SHA-256 해시** — truncation 시 무결성 검증용 |
| 🆕 `new_value_hash` | VARCHAR(64)? | **🆕 new_value의 SHA-256 해시** |
| 🆕 `edit_sequence_num` | INT | **🆕 snapshot_id + field 내 순차 번호** — "3번째 편집" UI 표시용 |

**🆕 추가 인덱스**: `(snapshot_id, edited_at DESC)`, `(field, edited_at DESC)`, `(edited_by, edited_at DESC)`

#### 🆕 `qa_edit_draft` — 편집 중인 임시 저장

관리자가 편집 중 저장한 **아직 반영되지 않은** 초안

| 컬럼 | 타입 | 설명 |
|------|------|------|
| `draft_id` | UUID PK | |
| `snapshot_id` | FK → qa_trend_snapshot | |
| `field` | VARCHAR(20) | 편집 대상 필드 |
| `draft_content` | TEXT | 임시 저장된 내용 |
| `saved_by` | VARCHAR(40) | 저장자 |
| `saved_at` | DATETIME | 저장 시각 |
| `expires_at` | DATETIME | **자동 만료 시각** (saved_at + 72시간, 만료된 초안은 표시되지 않음 · 시간당 배치로 정리) |

**제약조건**: `UNIQUE(snapshot_id, field, saved_by)` — admin별로 별도 초안 저장. 동일 snapshot+field+admin 조합은 덮어쓰기.

> **목적**: 관리자가 편집을 잠시 중단해도 내용이 유지됨. 여러 관리자가 동시 편집 시 충돌 감지에 사용. Admin A와 Admin B는 각자 자신의 초안을 가질 수 있으며 서로 덮어쓰지 않음.

## 4. 통찰 생성 엔진 (Insight Engine) 🆕

이것이 이 설계의 핵심이다. 단순 집계가 아니라 **LLM이 직접 분석하여 통찰을 생성**한다.

### 4.1 생성 파이프라인

```
질문 클러스터 완료 (canonical_text + raw_variants + counts 결정됨)
        │
        ▼
┌───────────────────────────────────────────────────────────┐
│ Step 1: 근본 원인 분석 (root_cause_analysis)                │
│                                                           │
│ LLM Prompt:                                               │
│ "다음 질문이 중독 회복 커뮤니티에서 342회 반복되었습니다.    │
│  질문: '중독에서 벗어나려면 어떻게 해야 하나요?'             │
│  변형: ['중독 탈출하는 방법', '중독 극복하려면', ...]        │
│                                                           │
│  다음을 분석해 주세요:                                      │
│  1. 이 질문이 반복되는 심리적·영적 근본 원인은 무엇인가?      │
│  2. 질문자들이 진짜 원하는 것은 무엇인가? (표면 vs 본질)      │
│  3. 이 질문이 회복 여정의 어떤 단계에서 주로 나오는가?        │
│                                                           │
│  200자 이내로 작성. 따뜻하고 공감적인 어조."                  │
└───────────────────────────┬───────────────────────────────┘
                            │
                            ▼
┌───────────────────────────────────────────────────────────┐
│ Step 2: AI 진단 요약 (ai_diagnosis)                        │
│                                                           │
│ LLM Prompt:                                               │
│ "당신은 이 질문에 대해 AI 상담사로서 답변했습니다.            │
│  질문: '중독에서 벗어나려면 어떻게 해야 하나요?'             │
│  당신의 답변: [실제 best_answer_text]                      │
│                                                           │
│  다음을 설명해 주세요:                                      │
│  1. 이 질문의深层 구조 — 질문자가 미처 말하지 못한 진짜 고민   │
│  2. 당신이 답변에서 특히 강조한 핵심 포인트 2가지            │
│  3. 이 답변이 단순한 조언이 아니라 '회복의 관점 전환'을       │
│     어떻게 유도했는지                                       │
│                                                           │
│  250자 이내. 분석적이되 전문용어 없이 일상 언어로."           │
└───────────────────────────┬───────────────────────────────┘
                            │
                            ▼
┌───────────────────────────────────────────────────────────┐
│ Step 3: 도움된 이유 분석 (best_answer_why)                  │
│                                                           │
│ LLM Prompt:                                               │
│ "이 답변은 28명의 👍와 2명의 👎를 받았습니다 (93% 긍정).     │
│  질문: '중독에서 벗어나려면 어떻게 해야 하나요?'             │
│  답변: [best_answer_text]                                 │
```

### 4.2 통찰 생성 주기

| 항목 | 주기 | 비고 |
|------|------|------|
| 빈도 집계 | 1분 | 빠른 통계 |
| 통찰 생성 | **질문이 Top 20 진입 시 최초 1회** | LLM 비용 고려 |
| 통찰 재생성 | **관리자 수동 트리거** 또는 **주간 배치** | 답변 패턴 변화 반영 |
| FB Ratio 갱신 | 1분 | 실시간 |

### 4.3 LLM 비용 추정

- 질문당 4회 LLM 호출 (원인분석 + AI진단 + 도움분석 + 성찰질문)
- Top 20 기준: 최초 80회, 이후 주간 재생성 80회
- GPT-4o-mini 기준: 월 약 $0.50 ~ $1.00 (매우 저렴)
- 기존 사용 중인 LLM (`hunyuan`, `deepseek` 등) 으로 대체 가능

## 5. 집계 알고리즘 (기존)

### 5.1 질문 클러스터링 (유사도 기반)

```
Raw Questions DB → 정규화 → 임베딩 벡터화 → 코사인 유사도 > 0.85 → 클러스터 병합 → canonical_text 선정
```

**정규화 규칙**:
- 한글 자모 정규화 (NFC)
- 불필요한 공백·줄바꿈 제거
- 말줄임표 통일 (… → ...)
- `?`, `??` → `?` 로 통일
- "기도제목", "기도 제목" → "기도제목"

**canonical_text 선택**: 클러스터 내 가장 짧고 완전한 형태

### 5.2 트렌드 점수 계산

```
trend_score = (count_7d × 3.0) + (count_30d × 1.0) + (fb_ratio × 0.5)
```

- 최근 질문에 3배 가중치
- 호평 비율도 긍정 신호로 반영

### 5.3 호평 답변 순위 (FB Ratio)

```
fb_ratio = (positive / (positive + negative)) × 100
```

- **최소 피드백 수**: 3개 이상의 평가가 있어야 순위에 포함
- **신뢰 구간 보정**: Wilson Score Interval 적용 (적은 표본에서 과대평가 방지)

### 5.4 집계 주기

- **실시간 근사치**: 1분 단위 배치 집계 (백그라운드 태스크 or 스케줄러)
- **정확 집계**: 매일 새벽 3시 전체 재계산
- **사용자 노출**: 최신 스냅샷 기준 (stale 최대 1분)

#### 🆕 `PATCH /admin/trending/{snapshot_id}` — 질문/답변/통찰 필드 직접 수정

**관리자가 AI 생성 콘텐츠가 틀렸을 때 직접 수정하는 핵심 API**

##### Request Body

```json
{
  "field": "question",
  "new_value": "관리자가 수정한 올바른 질문 텍스트",
  "edit_reason": "원문에 오타 및 비문 포함. 의미를 해치지 않는 선에서 다듬음",
  "save_draft": false
}
```

**`field` 가능한 값** (9종):

| field 값 | 대상 컬럼 | 타입 | 비고 |
|----------|----------|------|------|
| `question` | `canonical_text` | TEXT | 원본 텍스트는 `raw_variants`로 이동됨 |
| `answer` | `admin_edited_text` | TEXT | 사용자 노출 시 `admin_edited_text ?? best_answer_text` 우선순위 |
| `root_cause` | `root_cause_analysis` | TEXT | |
| `ai_diagnosis` | `ai_diagnosis` | TEXT | |
| `best_answer` | `best_answer_text` | TEXT | 캐시 직접 수정 (원본 interaction.answer는 변경 안 됨) |
| `best_answer_why` | `best_answer_why` | TEXT | |
| `reflection` | `reflection_prompt` | TEXT | |
| `is_featured` | `is_featured` | BOOL | |
| `is_hidden` | `is_hidden` | BOOL | |

**`save_draft` 플래그**:
- `false` (기본): 즉시 DB 반영 + 검수 완료 마킹 + edit_log 기록 + 사용자에게 새 버전 노출
- `true`: `qa_edit_draft` 테이블에 임시 저장 (72시간 유효). 실제 DB에는 반영되지 않음.

##### Response (TEXT 필드 수정 시)

```json
{
  "ok": true,
  "snapshot_id": "uuid",
  "field": "root_cause",
  "previous_value": "AI가 생성한 원본 근본 원인 분석 텍스트...",
  "new_value": "관리자가 수정한 올바른 텍스트...",
  "edited_by": "admin@example.com",
  "edited_at": "2026-07-16T15:00:00Z",
  "edit_log_id": "log-uuid",
  "diff_summary": "3문장 수정, '죄책감'→'은혜' 용어 변경, 성경 구절 인용 추가",
  "review_status_updated": true,
  "warnings": []
}
```

**`warnings` 예시** — 품질 경고가 있을 때:
```json
{
  "ok": true,
  "warnings": [
    {
      "type": "length_warning",
      "message": "수정된 텍스트가 50자 미만입니다. 더 자세한 설명을 권장합니다.",
      "current_length": 42,
      "recommended_min": 50
    }
  ]
}
```

##### Error Responses

| 상태 코드 | 상황 | 응답 예시 |
|-----------|------|----------|
| `200` | No-op (변경 없음) | `{"ok": true, "no_change": true}` |
| `404` | snapshot_id가 존재하지 않거나 soft-deleted | `{"detail": "스냅샷을 찾을 수 없습니다"}` |
| `409` | **동시 편집 충돌** — 다른 관리자가 5분 이내 동일 필드 수정 | `{"detail": "admin2@example.com님이 3분 전 이 필드를 수정했습니다", "conflict_with": "admin2@...", "conflict_at": "2026-07-16T15:03:00Z"}` |
| `422` | field 값이 유효하지 않음 | `{"detail": "유효하지 않은 필드입니다: invalid_field"}` |
| `422` | new_value 타입 불일치 (BOOL 필드에 문자열) | `{"detail": "is_featured 필드는 true/false 값만 허용됩니다"}` |
| `422` | TEXT 필드 최소 길이 미달 | `{"detail": "root_cause는 최소 20자 이상이어야 합니다 (현재: 8자)"}` |
| `422` | `is_featured=true` & `is_hidden=true` 동시 요청 | `{"detail": "is_featured와 is_hidden은 동시에 True일 수 없습니다"}` |
| `422` | `edit_reason` 200자 초과 | `{"detail": "수정 사유는 200자를 초과할 수 없습니다 (현재: 245자)"}` |
| `429` | Rate limit 초과 (편집: 분당 30회) | `{"detail": "너무 많은 요청입니다. 10초 후 다시 시도해 주세요", "retry_after": 10}` |

### 7.5 점진적 공개 (Progressive Disclosure)

사용자가 한 번에 모든 정보에 압도되지 않도록 설계:

```
카드 진입 시 보이는 것 (Level 1):
  · "342명이 함께 고민합니다"
  · 질문 텍스트
  · "💡 왜 이 질문이 많을까요? →"

탭 후 펼쳐지는 것 (Level 2):
  · 1️⃣ 근본 원인 분석
  · ↓ 스크롤

스크롤 다운 시 (Level 3):
  · 2️⃣ AI 진단 요약
  · ↓ 스크롤

하단 도달 시 (Level 4):
  · 3️⃣ 실제 도움된 답변 + 도움된 이유
  · 4️⃣ 당신을 위한 성찰 질문
  · [💬 직접 물어보세요]
```

```python
# app.py session_state 확장
st.session_state.insight_panel = None  # None | snapshot_id
```

### 8.8 AI 오류 수정 시나리오 — 실제 워크플로우 예시

**시나리오**: AI가 생성한 근본 원인 분석에 신학적 오류가 있음

```
1️⃣ 발견
   관리자가 🧠 통찰 검수 탭에서 새로 생성된 통찰 검토 중
   근본 원인 분석에 "중독은 죄의 결과이며 회개만이 유일한 해결책입니다"라는
   지나치게 단정적이고 정죄하는 표현 발견
   
   → [❌ 반려] 클릭

2️⃣ 반려 + LLM 재생성 지시
   반려 사유: "중독자를 '죄인'으로 정죄하는 어조. 요한복음 8:11 '나도 너를
   정죄하지 아니하노니'의 예수님 어조로 다시 작성 필요"
   
   추가 지시: "중독은 질병의 성격도 있음을 인정하고, 정죄가 아닌
   은혜의 관점에서 설명해 주세요."
   
   모델 변경: deepseek-v4 선택 (다른 모델로 시도)
   
   → [반려 + LLM 재생성] 클릭

3️⃣ 재생성 결과 재검토
   deepseek-v4 결과: "중독은 단순한 의지의 문제가 아닌, 몸과 마음과 영이
   함께 영향을 받는 복합적 상태입니다..."
   
   → 어조는 나아졌지만, 이번에는 너무 의학적이고 복음 메시지가 약함

4️⃣ 직접 수정 결정
   → [✏️ 수정] 클릭 → ✏️ 콘텐츠 편집 탭으로 이동
   
   AI 원본 (gemini)과 재생성본 (deepseek) 두 버전을 참고하여
   최적의 텍스트로 직접 편집:
   
   "중독은 단순한 의지의 문제가 아닙니다. 몸과 마음과 영이 함께
   영향을 받는 복합적 상태입니다. 예수님은 간음한 여인에게 '나도 너를
   정죄하지 아니하노니 가서 다시는 죄를 범하지 말라'(요 8:11)고 말씀하셨습니다.
   정죄가 아닌 은혜, 그리고 '다시는'이라는 새로운 시작의 약속 —
   이것이 회복의 출발점입니다."

5️⃣ 미리보기로 사용자 화면 확인
   → [👁 미리보기] 클릭 → 사용자에게 보일 통찰 패널 확인
   
6️⃣ 저장
   수정 사유: "gemini 버전(정죄적) + deepseek 버전(의학적) 장점 통합,
   요한복음 8:11 중심으로 재구성"
   → ☑️ 확인 체크 → [💾 검토 완료 및 저장]
   
7️⃣ 결과
   - root_cause_analysis = 수정된 텍스트
   - review_status_root_cause = "approved"
   - edit_log에 상세 변경 이력 기록 (old_value=두 AI 버전, new_value=수동 편집본)
   - 사용자에게 즉시 새 버전 노출
```

**소요 시간**: 약 3-5분 (발견 → 반려 → 재생성 → 재검토 → 수동 편집 → 저장)

### 8.10 📊 트렌드 차트 탭 (기존 확장)

기존 설계와 동일하나 **통찰 품질 추적** 차트 추가:

- **필드별 평균 편집 횟수** (방사형 차트): 어떤 필드가 가장 자주 수정되는지

### 11.2 편집 가이드라인 (관리자용)

편집기 상단에 항상 표시되는 가이드라인:

```
📝 편집 가이드:
```

### 11.4 개인정보
- `question`과 `answer`는 `subscriber_id`와 분리하여 집계 (익명화)

- 통찰 생성 시 실제 사용자 데이터는 LLM에 전달되지 않음 (통계만 전달)

### 11.5 콘텐츠 품질
- **통찰 데이터는 관리자 검수 전까지 사용자에게 노출되지 않음**

- 기존 Safety 모듈로 질문/답변 콘텐츠 자동 필터링
- 관리자 `is_hidden` 플래그로 즉시 대응 가능

### 12.1 데이터 모델 — 누락된 제약조건 & 타입 안전성

#### 12.1.1 `qa_trend_snapshot` 보완 사항

| # | 항목 | 현재 상태 | 이슈 | 보완 |
|---|------|----------|------|------|
| 1 | `created_at` / `updated_at` | 없음 (`computed_at`만 존재) | 스냅샷 최초 생성일과 마지막 수정일 추적 불가 | `created_at DATETIME NOT NULL DEFAULT (utcnow)`, `updated_at DATETIME NOT NULL DEFAULT (utcnow)` 추가 |
| 2 | `published_at` | 없음 | "사용자에게 최초 공개된 시점" 추적 불가. 검수 완료 후 노출 타이밍 분석에 필요 | `published_at DATETIME?` 추가. 4개 insight + question + answer 모두 approved 되는 순간 자동 설정 |
| 3 | `deleted_at` (soft delete) | 없음 | 실수로 삭제 시 복구 불가. GDPR "잊힐 권리" 대응 시 데이터를 물리적으로 삭제할지 소프트 삭제할지 모호 | `deleted_at DATETIME?` 추가. `deleted_at IS NOT NULL`인 행은 모든 API에서 제외 |
| 4 | `review_status_*` 타입 | `VARCHAR(10)?` | "pending"/"approved"/"rejected" 외의 값이 들어갈 수 있음 (타입 불안정) | `ENUM('pending','approved','rejected')` 또는 Python `enum.StrEnum` + CHECK 제약조건 |
| 5 | `is_featured` / `is_hidden` 기본값 | 명시 안 됨 | NULL vs FALSE 혼동 가능 | `NOT NULL DEFAULT FALSE` 명시 |
| 6 | `needs_regeneration` 기본값 | 명시 안 됨 | ditto | `NOT NULL DEFAULT FALSE` |
| 7 | `insight_version` 기본값 | 명시 안 됨 | 첫 생성 시 NULL → 0 → 1? 혼란 | `NOT NULL DEFAULT 0` (통찰 미생성 상태), 생성 시 1로 설정 |
| 8 | `fb_ratio` nullable | `FLOAT` | positive+negative=0일 때 NULL vs 0? | `FLOAT DEFAULT 0.0` — 피드백 없을 때는 0.0으로 처리하고, UI에서 "평가 부족" 표시 |
| 9 | `best_answer_id` 타입 | `VARCHAR(40)?` | interaction.interaction_id도 VARCHAR(40)인지 확인 필요 — UUID면 길이 불일치 | `interaction_id`와 동일 타입으로 통일 |
| 10 | `admin_edited_text` 의미 모호 | `TEXT?` | answer를 수정한 건지 question을 수정한 건지 불분명. 다른 필드들은 각자 컬럼이 있는데 answer만 이 컬럼에 의존 | `answer` 수정본은 `admin_edited_text` 유지, `question` 수정본은 `canonical_text` 직접 업데이트 + 원본을 `raw_variants`로 이동. 또는 `admin_edited_text`를 `admin_edited_answer`로 renamed |

### 12.2 API 계층 — 누락된 검증, 예외 처리, 경계 조건

#### 12.2.1 `PATCH /admin/trending/{snapshot_id}` 보완

| # | 이슈 | 보완 |
|---|------|------|
| 1 | **입력값 검증 누락** — `new_value`가 공백만 있는 문자열, 제어문자, XSS 스크립트를 포함할 수 있음 | Pydantic `field_validator`: `strip()` 후 empty 체크, `<script>` 태그 필터링, 유니코드 제어문자(\\u0000-\\u001f) 제거 |
| 2 | **No-op 감지 누락** — `new_value`가 현재 DB 값과 완전히 동일할 때 | 현재 값과 비교하여 동일하면 `200 {"ok": true, "no_change": true}` 반환 (edit_log 기록 안 함) |
| 3 | **BOOL 필드 검증** — `is_featured`/`is_hidden`에 `new_value`가 `"true"` 문자열 등 | Pydantic에서 `bool` 타입 강제. `"true"`, `"false"`, `1`, `0`만 허용하고 나머지는 422 |
| 4 | **`is_featured`와 `is_hidden` 동시 True** | 비즈니스 규칙 위반. 둘 다 True 요청 시 422 `{"detail": "is_featured와 is_hidden은 동시에 True일 수 없습니다"}` |
| 5 | **409 충돌 윈도우 정밀화** | "5분 이내 동일 필드 수정" → **"다른 admin이 동일 필드를 마지막으로 저장한 지 5분 이내일 때, 현재 admin이 해당 필드를 편집 중이었음을 서버가 알지 못하는 경우"** 로 구체화. 추가로 `If-Unmodified-Since` 헤더 지원 (낙관적 잠금) |
| 6 | **편집 충돌 해결 전략** | 현재는 경고만 함. 추가로 "내 변경 사항을 유지하고 충돌 무시" 옵션 필요 (`force: true` 파라미터) |
| 7 | **글자 수 검증 경계값** | "50자 미만 경고" → 각 필드별 권장 범위 테이블화. 경고는 `warnings[]`에 포함되지만 저장은 허용. **최소 길이(10자) 미만은 422로 차단** (실수 방지) |
| 8 | **`edit_reason` 길이** | VARCHAR(200) → 초과 시 truncate가 아니라 422 반환 |

| `question` | 10자 | 20자 | 150자 | 500자 |

| `root_cause` | 20자 | 80자 | 250자 | 500자 |

### 12.3 Insight Engine — 누락된 예외 처리 & LLM 장애 대응

#### 12.3.1 LLM 호출 실패 시나리오

| 시나리오 | 현재 상태 | 보완 |
|----------|----------|------|
| LLM API 타임아웃 (30초) | 미정의 | `asyncio.wait_for(chat_with_fallback(...), timeout=30.0)`. 타임아웃 시 `TimeoutError` → 해당 섹션만 `None`으로 두고 나머지 섹션 계속 진행 |
| LLM Rate Limit (429) | 미정의 | `chat_with_fallback`에 이미 fallback 체인 있음. 3회 retry with exponential backoff (1s, 2s, 4s). 모두 실패 시 해당 섹션 `None` |
| LLM 응답이 빈 문자열 | 미정의 | 빈 응답 → `None` 처리 + 경고 로그 |
| LLM 응답이 글자 수 제한 초과 | 미정의 | 프롬프트의 `max_tokens`로 제한. 초과 응답은 truncate (말미에 `...`). `insight_generated_at`에 표시하고 관리자 검수 유도 |
| 전체 4개 섹션 중 2개만 성공 | 미정의 | 부분 성공으로 저장. 실패 섹션은 `None`, 성공 섹션은 `review_status = "pending"`. `needs_regeneration = True` (실패 섹션 자동 재시도). 주간 배치에서 `needs_regeneration=True` + 해당 섹션 `NULL`인 항목 우선 재생성 |
| `best_answer_text`가 NULL (피드백 있는 답변 없음) | 미정의 | Step 3 (best_answer_why) 스킵. `best_answer_id`, `best_answer_text`, `best_answer_why` 모두 NULL. UI에서는 "아직 충분한 평가를 받은 답변이 없습니다" 표시 |

#### 12.3.2 프롬프트 관리

| # | 이슈 | 보완 |
|---|------|------|
| 1 | 프롬프트 버전 관리 없음 | `insight_prompt_version VARCHAR(10)` 필드를 `qa_trend_snapshot`에 추가. 프롬프트 변경 시 버전 증가, 기존 생성물과의 매핑 가능 |
| 2 | `additional_instruction` 길이 제한 | 500자로 제한. 초과 시 422. 프롬프트 injection 방지를 위해 마크다운 코드블록으로 감싸서 주입 |

#### 12.3.3 중복 생성 방지

| 시나리오 | 보완 |
|----------|------|
| 동일 canonical_text가 이미 통찰 있음 | `insight_version > 0`이면 신규 생성 대신 "이미 생성됨" 스킵. `needs_regeneration=True`인 경우에만 재생성 |
| Top 20 진입/이탈/재진입 | `insight_version > 0`이고 `needs_regeneration=False`면 재생성 안 함. 30일 이상 Top 20 밖에 있다가 재진입했을 때만 `needs_regeneration=True`로 마킹 |

| # | 항목 | 보완 |

| 1 | **임베딩 모델** | `text-embedding-3-small` (OpenAI) 또는 `hunyuan-embedding-20250716`. config.yml에서 지정 가능하게. Dimension: 1536 (OpenAI) / 1024 (Hunyuan) |

### 12.6 동시성 & 트랜잭션 — 상세 설계

#### 12.6.1 편집 충돌 시나리오 매트릭스

| Admin A | Admin B (동시) | 결과 |
|---------|---------------|------|
| 필드 F 편집 중 | **다른** 필드 G 편집 | 충돌 없음. 각자 저장 가능 |
| 필드 F 편집 중 | **같은** 필드 F 편집 | A가 먼저 저장 → B가 저장 시도 → 409 + "⚠️ 다른 관리자가 3분 전 이 필드를 수정했습니다" |
| 필드 F 편집 중 | 같은 필드 F, B가 `force=true` | B의 값으로 덮어쓰기. A의 변경은 edit_log에 preserved. `reverted=false` |
| 필드 F 저장 완료 (5분 경과) | 같은 필드 F 편집 | 충돌 감지 안 함 (5분 윈도우 초과) |
| 초안 저장 | 초안 저장 | admin별 별도 초안 (UNIQUE on saved_by). 충돌 없음 |

#### 12.6.2 트랜잭션 격리 수준

SQLite WAL 모드 기준:
- **읽기**: 다른 쓰기와 동시 가능 (WAL)
- **쓰기**: `get_session_immediate()`로 배타적 락 (SQLite는 단일 쓰기만 허용)

편집 저장 시 **`get_session_immediate()` 사용**하여 동시 쓰기 방지.

```python
def save_edit(snapshot_id: str, field: str, new_value: str, edited_by: str, edit_reason: str = None):
    with get_session_immediate() as s:
        snapshot = s.query(QATrendSnapshot).filter_by(snapshot_id=snapshot_id).first()
        if not snapshot:
            raise HTTPException(404)
        
        # 409 충돌 감지 (5분 윈도우)
        recent = s.query(QAAdminEditLog).filter(
            QAAdminEditLog.snapshot_id == snapshot_id,
            QAAdminEditLog.field == field,
            QAAdminEditLog.edited_by != edited_by,
            QAAdminEditLog.edited_at >= datetime.now(timezone.utc) - timedelta(minutes=5),
        ).first()
        if recent:
            raise HTTPException(409, detail=f"{recent.edited_by}님이 {recent.edited_at}에 편집")
        
        old_value = getattr(snapshot, _field_to_column(field))
        setattr(snapshot, _field_to_column(field), new_value)
        snapshot.updated_at = datetime.now(timezone.utc)
        
        log = QAAdminEditLog(snapshot_id=snapshot_id, field=field,
                            old_value=old_value, new_value=new_value,
                            edited_by=edited_by, edit_reason=edit_reason)
        s.add(log)
        s.flush()
```

### 12.11 편집 diff 생성 상세 (`edit_diff.py`)

```python
# backend/app/services/edit_diff.py

import difflib
from typing import Optional

def compute_diff(old_text: Optional[str], new_text: Optional[str]) -> dict:
    """두 텍스트의 diff를 생성하고 변경 요약을 반환.
    
    Returns:
        {
            "changed": bool,
            "added_chars": int,
            "removed_chars": int,
            "changed_sentences": int,
            "summary": str,  # "3문장 수정, 1문장 추가, 42자 증가"
            "added_bible_refs": list[str],  # 성경 구절 추가 감지
            "inline_diff_html": Optional[str],  # HTML diff (관리자 UI용)
        }
    """
    if old_text is None:
        old_text = ""
    if new_text is None:
        new_text = ""
    
    # 문장 단위 분리
    old_sentences = _split_sentences(old_text)
    new_sentences = _split_sentences(new_text)
    
    # diff
    matcher = difflib.SequenceMatcher(None, old_sentences, new_sentences)
    changed_sentences = sum(1 for tag, _, _, _, _ in matcher.get_opcodes() if tag != 'equal')
    
    # 성경 구절 패턴 감지 (요한복음 8:36, 요 8:11, etc.)
    import re
    bible_pattern = re.compile(r'(마태|마가|누가|요한|요한복음|로마서|고린도전서|고린도후서|갈라디아서|에베소서|빌립보서|골로새서|데살로니가전서|데살로니가후서|디모데전서|디모데후서|디도서|빌레몬서|히브리서|야고보서|베드로전서|베드로후서|요한일서|요한이서|요한삼서|유다서|요한계시록|창세기|출애굽기|레위기|민수기|신명기|여호수아|사사기|룻기|사무엘상|사무엘하|열왕기상|열왕기하|역대상|역대하|에스라|느헤미야|에스더|욥기|시편|잠언|전도서|아가|이사야|예레미야|예레미야애가|에스겔|다니엘|호세아|요엘|아모스|오바댜|요나|미가|나훔|하박국|스바냐|학개|스가랴|말라기)\s*\d+:\d+')
    old_refs = set(bible_pattern.findall(old_text))
    new_refs = set(bible_pattern.findall(new_text))
    added_bible_refs = list(new_refs - old_refs)
    
    char_diff = len(new_text) - len(old_text)
    
    parts = []
    if changed_sentences > 0:
        parts.append(f"{changed_sentences}문장 수정")
    if char_diff > 0:
        parts.append(f"{char_diff}자 증가")
    elif char_diff < 0:
        parts.append(f"{-char_diff}자 감소")
    if added_bible_refs:
        parts.append(f"성경 구절 {len(added_bible_refs)}건 추가 ({', '.join(added_bible_refs)})")
    
    return {
        "changed": old_text != new_text,
        "added_chars": max(0, char_diff),
        "removed_chars": max(0, -char_diff),
        "changed_sentences": changed_sentences,
        "summary": ", ".join(parts) if parts else "변경 없음",
        "added_bible_refs": added_bible_refs,
        "inline_diff_html": _generate_html_diff(old_text, new_text),
    }


def _split_sentences(text: str) -> list[str]:
    """한국어 문장 분리 (마침표, 물음표, 느낌표 기준)."""
    import re
    return [s.strip() for s in re.split(r'(?<=[.!?⋯…])\s+', text) if s.strip()]


def _generate_html_diff(old: str, new: str) -> Optional[str]:
    """HTML 기반 diff 생성 (관리자 UI에서 <span> 태그로 표시)."""
    if not old and not new:
        return None
    
    differ = difflib.HtmlDiff(wrapcolumn=60)
    return differ.make_table(
        old.splitlines(), new.splitlines(),
        context=True, numlines=2,
    )
```

## 13. 결론: 이 설계에서 가장 중요한 것

### 사용자에게
**"왜?"를 이해하는 경험** — 단순히 인기 질문을 나열하는 것이 아니라, 그 질문이 왜 나왔는지, AI는 어떻게 이해했는지, 그래서 무엇을 배울 수 있는지를 보여준다. 이것이 진정한 회복의 통찰이다.

### 관리자에게
**AI가 틀렸을 때 즉시 고칠 수 있는 도구** — LLM이 생성한 콘텐츠는 완벽하지 않다. 특히 신학, 심리학, 문화적 맥락에서는 더욱 그렇다. 관리자는 ✏️ 콘텐츠 편집 탭에서 AI 원본을 확인하고, 직접 수정하고, 미리보기로 사용자 화면을 확인한 후 저장할 수 있다. 모든 수정 이력은 📋 편집 이력 탭에서 추적 가능하며, 필요하면 언제든지 롤백할 수 있다.

### 3가지 핵심 숫자
- **2 클릭**: AI 오류 발견 → 수정 완료까지 최소 클릭 수
- **9개 필드**: 관리자가 직접 편집할 수 있는 콘텐츠 필드
- **100% 추적**: 모든 변경은 edit_log에 기록, 롤백 가능
