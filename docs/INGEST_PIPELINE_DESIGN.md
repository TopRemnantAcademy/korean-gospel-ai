# 📥 문서 재편집 + 청킹 파이프라인 기획안

> 목표: 새 설교/문서를 받으면 **AI(RAG)가 최대한 잘 활용할 수 있는 형태**로 자동 재편집하고,
> 검색 품질을 극대화하는 청크로 분할한다.
>
> 작성: Claude (개발 도구) / 런타임 LLM: DeepSeek (`.env: LLM_PROVIDER=deepseek`)
> 강도: **C 적극적** | 기법: ③의미청킹 + ④컨텍스트강화 + ⑦품질게이트

---

## 0. 핵심 원칙

1. **원문 의미 100% 보존** — 재편집은 "표현 다듬기"지 "내용 변경"이 아니다. 신학적 내용은 절대 불변.
2. **LLM 독립** — 모든 LLM 호출은 `chat_with_fallback()` 추상 계층 경유. DeepSeek/Gemini/OpenAI 교체는 `.env` 한 줄.
3. **단계별 멱등성** — 각 단계는 입력→출력이 결정적이고 재실행 안전. 중간 산출물을 DB에 보존(디버깅·롤백).
4. **품질 게이트 차단** — 검증 실패 청크는 인덱싱 진입 금지. "조용한 오염" 방지.
5. **비용 통제** — 적극 강도라도 LLM 호출 횟수를 문서당 상한으로 묶는다(섹션 수 비례, 청크 수 무관 배칭).

## 2. 단계별 상세 설계

### Stage 1 — 정규화 `normalizer.py` (규칙, LLM✗)

| 처리 | 방법 | 예시 |
|------|------|------|
| 구어체 필러 | 정규식 치환 | "어 그 뭐냐..", "음.." → 제거 |
| 반복어 | 연속 동일어절 축약 | "진짜 진짜 진짜" → "진짜" |
| 한글 성경표기 | 매핑 테이블 | "요한복음 삼장 십육절" → "요한복음 3:16" |
| 약어 통일 | 66권 정규화 | "요 3:16" → "요한복음 3:16" (옵션) |
| 공백/줄바꿈 | 정규식 | 3줄↑ → 2줄, 다중공백 → 1 |

- **위험 0** (규칙 기반, 의미 불변). 가장 먼저 적용해 LLM 입력을 깨끗하게.

### Stage 2 — 구조화 `restructurer.py` (LLM✓, DeepSeek)

- **입력**: 정규화된 평문 (수천~수만 자)
- **방법**: 긴 문서는 윈도우 단위로 분할 → 각 윈도우에 "섹션 헤딩 생성 + 구어체를 자연스러운 문어체로, **내용 추가·삭제 금지**" 프롬프트
- **출력**: `## 섹션제목` + 다듬은 본문 (마크다운)
- **비용 통제**: 윈도우 크기 ~3000자, 문서당 호출 = ⌈길이/3000⌉. 31KB 설교 ≈ 5회.
- **안전장치**: 출력 길이가 입력의 60% 미만이면 "내용 소실 의심" → 원문 유지 + 경고(품질게이트로).

### Stage 3 — 의미 단위 청킹 `chunker.py` 개선 (③)

**현재 문제점 (측정값):**
- 토큰 필드 없음 → 글자수(31~525)로만 관리, LLM 컨텍스트 한도 보장 불가
- 부스러기 청크 발생 (31자 1개)
- 단순 글자수 컷 → 문장 중간/주제 중간 절단 가능

**개선:**
1. `Chunk`에 `token_estimate` 추가 (한국어 휴리스틱: `chars * 0.55`, 또는 임베더 토크나이저 정확 계산)
2. 목표 크기 = **토큰 기준** (target 350, max 512 — KURE/BGE 한도 안전)
3. **섹션 헤딩 우선 경계**: Stage 2의 `##`를 1순위 분할점으로
4. **의미 경계 보조**: 한 섹션이 너무 길면 인접 문장 임베딩 코사인 유사도 계산 → 급락점(주제 전환)에서 분할
5. **부스러기 병합**: `min_tokens`(예: 50) 미만 청크는 앞/뒤 인접 청크에 흡수
6. overlap = 마지막 1문장 (현재 80자 → 문장 단위로)

### Stage 4 — 컨텍스트 강화 `contextualizer.py` (④, LLM✓)

- Anthropic Contextual Retrieval 기법 (LLM 무관, DeepSeek로 구현)
- 각 청크마다: `"이 청크는 '{제목}'의 '{섹션}' 부분으로, {핵심내용 한 줄}."` 생성
- **저장 구조**:
  - `embed_text` = `맥락 + "\n\n" + 본문` → **이것으로 임베딩**
  - `display_text` = 본문만 → **사용자/LLM에 표시**
- **효과**: 대명사·생략 많은 한국어 설교에서 검색 정확도 크게 향상
- **비용 통제**: 청크별 1회지만 max_tokens 작게(~80), 배칭. 문서당 = 청크 수.
  - 절감 옵션: 섹션 맥락은 섹션당 1회 생성 후 청크에 공유 → 호출 = 섹션 수.

### Stage 6 — 적극 추가물 (C 강도, LLM✓)

| 산출물 | 용도 | 저장 |
|--------|------|------|
| 섹션 요약 | 검색 미리보기, 재순위 신호 | DocumentVersion.summary 확장 |
| Q&A 쌍 | 가상질문을 별도 인덱싱 → recall↑ | 신규 테이블 or payload |

- Q&A: "이 섹션이 답할 수 있는 질문 3개 생성" → 질문 텍스트도 임베딩해 같은 청크로 라우팅 (역방향 HyDE).

### Stage 7 — 품질 게이트 `quality_gate.py` (⑦)

**인덱싱 직전 자동 검증, 실패 시 차단:**

| 검사 | 기준 | 실패 처리 |
|------|------|----------|
| 빈 청크 | len==0 | 제거 |
| 중복 청크 | 본문 해시 일치 | 제거(1개만 유지) |
| 과소 청크 | < min_tokens | 병합 시도, 실패 시 경고 |
| 과대 청크 | > max_tokens | 강제 재분할 |
| 의미 보존 | 원문 핵심어(명사/신학어) 유지율 < 85% | **차단** + 리포트 |
| 신학 왜곡 | safety_service 패턴 매칭 | **차단** + 리포트 |
| 성경 오인용 | 66권 화이트리스트 외 | 경고 |

- 게이트 결과는 `IndexSnapshot`/audit에 기록 → 관리자 추적 가능.

## 3. 데이터 모델 변경

```
DocumentVersion (확장)
  + structured_body   : Text  (Stage 2 산출, null=미처리)
  + section_summaries : JSON  (Stage 6)

Chunk payload (Qdrant, 확장)
  + context_prefix : str   (Stage 4 맥락 한 줄)
  + section_title  : str
  + token_estimate : int
  + qa_questions   : list[str]  (Stage 6, 선택)

신규 테이블 (선택): GeneratedQA(version_id, chunk_seq, question, embed_vector)
```

## 4. 구현 순서 (선택된 우선순위 반영)

| # | 작업 | 의존 | LLM | 위험 |
|---|------|------|-----|------|
| **1** | **청킹 파일 수리** (토큰 필드 + 부스러기 병합) | — | ✗ | 낮음 |
| 2 | 품질 게이트 ⑦ (규칙 검사부터) | 1 | ✗ | 낮음 |
| 3 | 정규화 Stage 1 | — | ✗ | 낮음 |
| 4 | 구조화 Stage 2 (DeepSeek) | 3 | ✓ | 중 |
| 5 | 의미 경계 청킹 ③ (임베딩 유사도) | 1,4 | ✗ | 중 |
| 6 | 컨텍스트 강화 ④ (DeepSeek) | 5 | ✓ | 중 |
| 7 | 적극 추가물 (요약·Q&A) | 4 | ✓ | 중 |
| 8 | 파이프라인 오케스트레이터 + publish 연결 | 전체 | — | 중 |

- **1·2번부터** 착수 (LLM 없이 즉시 효과, 기초 안정화).
- 각 단계는 feature flag(`.env`)로 on/off → 점진 배포·롤백 안전.

## 5. 비용·속도 추정 (DeepSeek, 31KB 설교 기준)

| 단계 | LLM 호출 | 예상 시간 |
|------|---------|----------|
| Stage 2 구조화 | ~5회 (윈도우) | ~25s |
| Stage 4 컨텍스트 | 섹션당 1회 ≈ 6회 | ~30s |
| Stage 6 요약/QA | 섹션당 1회 ≈ 6회 | ~30s |
| **합계** | **~17회** | **~1.5분/문서** |

- 업로드는 **비동기 job**(이미 존재)으로 처리 → 사용자 대기 없음.
- 채팅 응답 속도와 무관 (인덱싱은 사전 1회).
