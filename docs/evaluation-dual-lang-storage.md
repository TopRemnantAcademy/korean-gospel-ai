## 1. 기술적 복잡도 및 구현 난이도 평가

### 1.1 필요한 DB 스키마 변경 (20+ 컬럼 추가)

이원화 저장을 위해 수정해야 하는 테이블과 컬럼:

| 테이블 | 현재 컬럼 | 추가 필요 컬럼 | 영향도 |
|--------|-----------|----------------|--------|
| `interaction` | `question` (Text) | `question_zh` (Text) | **매우 높음** — 모든 채팅 응답에 번역 발생 |
| `interaction` | `answer` (Text) | `answer_zh` (Text) | **매우 높음** — 핵심 콘텐츠 |
| `qa_trend_snapshot` | `canonical_text`, `root_cause_analysis`, `ai_diagnosis`, `best_answer_text`, `best_answer_why`, `reflection_prompt` (6개 Text) | 각각 `_zh` 버전 (6개 컬럼 추가) | 중간 |
| `document_version` | `title`, `summary`, `body_patch`, `structured_body` (4개) | 각각 `_zh` 버전 (4개 컬럼 추가) | 중간 |
| `prompt_template` | `content` (Text) | `content_zh` (Text) | 낮음 |
| `clarifier` 응답 | 임시 생성 | 저장 시 번역 필요 | 낮음 |

**총 신규 컬럼**: 약 14~16개  
**Alembic 마이그레이션**: 신규 마이그레이션 1회 + 모든 기존 데이터 NULL 처리

### 1.2 번역 파이프라인 구현 복잡도

```
한국어 콘텐츠 생성 → [번역 트리거] → LLM 번역 호출 → 검증 → ZH 컬럼 저장
```

| 단계 | 난이도 | 설명 |
|------|--------|------|
| 번역 트리거 | 중간 | 모든 콘텐츠 생성 지점에 번역 후크 삽입 필요 (chat.py, insight_engine.py, greeting_service.py, clarifier.py 등 6개 이상 파일) |
| 비동기 처리 | 높음 | 번역을 동기 처리하면 응답 지연 2~5초 증가. 비동기면 실패 처리, 재시도, 상태 추적 필요 |
| LLM 번역 품질 | 중간 | 기존 `translation.py` 인프라 재사용 가능하나, 대화체 번역은 문서 번역보다 더 까다로움 |
| 번역 검증 | 높음 | 신학 용어 오역 시 심각한 문제. 현재 glossary 30개 항목으로 부족 가능성 |
| 실패 처리 | 높음 | 번역 실패 시 원문만 저장? 재시도? 실패 알림? |

**구현 예상 공수**: 5~8인일 (백엔드 3~4일, 테스트 1~2일, 모니터링 1~2일)

### 1.3 번역 품질 리스크 (신학 콘텐츠 특수성)

복음/신학 콘텐츠의 번역은 일반 텍스트보다 훨씬 위험:

```
한국어: "예수님의 보혈로 죄 사함을 받았습니다"
❌ GPT 직역: "因耶稣的血得到罪的赦免" (어색, 가톨릭 어감)
✅ 기독교 용어: "因耶稣的宝血罪得赦免" (보혈=宝血, 개신교 표준)
```

**실제 오역 위험 사례**:
- `은혜` → `恩惠`(일반) vs `恩典`(신학)
- `성령 충만` → `被圣灵充满` vs `圣灵充满` (피동/능동)
- `십자가` → `十字架` (정확하나 문맥 따라 의미 변화)

**용어집 부족**: 현재 30개 용어로는 실제 대화에서 등장하는 모든 신학 용어를 커버 불가능.

## 2. 운영 관점의 실질적 필요성 및 유지보수 부담

### 2.1 현재 사용자 규모 및 중국어 수요

| 질문 | 답변 | 근거 |
|------|------|------|
| 중국어 사용자가 실제로 존재하는가? | **확인 불가** | `subscriber` 테이블에 `lang` 컬럼 없음 |
| 중국어 채팅 요청 비율은? | **추적 안 됨** | `interaction` 테이블에 `target_lang` 저장 안 함 |
| 중국어 UI 요구가 있는가? | **없음** | 전체 UI가 한국어, 설정에도 언어 옵션 없음 |

**핵심 문제**: 중국어 사용자의 존재 여부조차 데이터로 확인할 수 없는 상태에서 이원화 저장 투자는 시기상조.

### 2.2 스토리지 비용 분석

| 항목 | 현재 (KO only) | 이원화 (KO+ZH) | 증가율 |
|------|---------------|----------------|--------|
| interaction.answer (평균 500자) | 500자 | 500 + 400 = 900자 | **+80%** |
| qa_trend_snapshot (6개 Text, 합계 ~3,000자) | 3,000자 | 3,000 + 2,400 = 5,400자 | **+80%** |
| document_version (4개 Text, 합계 ~10,000자) | 10,000자 | 10,000 + 8,000 = 18,000자 | **+80%** |

**월간 예상 추가 비용**:
- DB 스토리지: 현재 규모에서는 무시 가능 (수 GB 이내)
- LLM 번역 API 비용: **주요 비용 요소**
  - 대화 1건당 약 500토큰(입력+출력) × 일 100건 = 50,000토큰/일
  - DeepSeek 기준 월 약 $5~15
  - Hunyuan 기준 월 약 ¥30~80
  - → 현재 사용량이 적다면 비용도 미미하지만, 확장 시 선형 증가

### 2.3 유지보수 부담

| 항목 | 부담 수준 | 설명 |
|------|-----------|------|
| 용어집 관리 | 중간 | 신규 신학 용어 지속 추가 필요 |
| 번역 품질 모니터링 | **높음** | 신학 오역은 자동 감지 어려움, 수동 검수 필요 |

## 3. 대안 분석

### 대안 A: 이원화 저장 (현 제안)

```
생성 시 KO → 즉시 번역 → KO + ZH 동시 저장
```

| 장점 | 단점 |
|------|------|
| 중국어 응답 즉시 제공 (지연 0) | 모든 콘텐츠에 번역 비용 발생 (사용 여부 무관) |
| ZH 검색/분석 가능 | DB 스키마 복잡도 2배 |
| 오프라인 사용 가능 | 편집/롤백 시 ZH 동기화 추가 구현 |

### 대안 B: 요청 시 실시간 번역 (기존 인프라 활용)

```
저장은 KO만 → 중국어 요청 시 LLM 실시간 번역 → 응답
```

| 장점 | 단점 |
|------|------|
| 구현 불필요 (이미 `target_lang` 존재) | 중국어 응답 시 1~2초 추가 지연 |
| 번역 비용: 사용한 만큼만 | 매 요청마다 번역 (캐싱 없음) |
| DB 스키마 변경 없음 | - |
| 유지보수 부담 0 | - |

### 대안 C: 하이브리드 (선택적 캐싱)

```
인기 콘텐츠만 번역 캐싱 + 일반 콘텐츠는 실시간 번역
```

| 장점 | 단점 |
|------|------|
| 자주 조회되는 콘텐츠만 ZH 저장 | 캐싱 판단 로직 추가 필요 |
| 비용 효율적 | 구현 복잡도 중간 |
| 번역 품질 검증에 집중 가능 | 콘텐츠 유형별 분기 처리 |

## 4. 최종 판단

### 4.1 냉정한 평가 매트릭스

| 평가 항목 | 점수 (1~5) | 가중치 | 점수×가중치 |
|-----------|-----------|--------|-------------|
| 실제 비즈니스 필요성 | 1 | ×35% | 0.35 |
| 기술적 구현 난이도 (낮을수록 좋음) | 2 | ×25% | 0.50 |
| 운영 유지보수 부담 (낮을수록 좋음) | 2 | ×20% | 0.40 |
| 사용자 경험 개선 효과 | 2 | ×15% | 0.30 |
| 확장성/미래 대비 | 3 | ×5% | 0.15 |
| **종합 점수** | | | **1.70 / 5.00** |

- 비즈니스 필요성: 중국어 사용자 존재 여부조차 확인되지 않음 → 1점
- 기술적 구현 난이도: 중간~높음, 14+ 컬럼 추가, 6+ 파일 수정 → 2점 (낮을수록 좋음의 역수)
- 유지보수 부담: 용어집 관리, 품질 모니터링, 동기화 → 2점
- UX 개선: 실제 수요 없음 → 2점

### 4.2 판결: **도입하지 않는다** ❌

**이유 요약:**

1. **해결하려는 문제가 실재하지 않는다** — 중국어 사용자 규모, 수요, 요청 비율에 대한 어떤 데이터도 없다. 존재하지 않는 문제를 위해 시스템 복잡도를 2배로 늘리는 것은 과잉 설계다.

2. **이미 해결책이 있다** — `target_lang="zh"` 파라미터 하나로 중국어 응답을 실시간 생성할 수 있다. 추가 구현 0줄. 지연 시간 1~2초는 LLM 응답 자체의 수 초 대비 무시할 만하다.

3. **신학 콘텐츠 번역 품질 리스크** — `보혈→宝血`, `은혜→恩典` 같은 용어 오역 한 건이 사용자 신뢰를 무너뜨릴 수 있다. 이원화 저장은 "저장된 번역이 검증되었다"는 기대를 주지만, 실제로 모든 번역을 검증하는 것은 불가능하다. **실시간 번역이 더 솔직하다** — "AI가 방금 번역했습니다"라고 말할 수 있다.

4. **비용 대비 효과 없음** — 모든 콘텐츠를 번역하는 LLM API 비용 + DB 복잡도 + 유지보수 비용이 현재 증명되지 않은 수요를 위한 투자로 타당하지 않다.
