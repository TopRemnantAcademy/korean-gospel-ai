### 2.2 "스트리밍 미들웨어 버퍼링" 의심 — **버그 아님으로 정정** ⚪

과거 분석에서 `BaseHTTPMiddleware`(RateLimit/RequestID)가 스트리밍 채팅(`/chat/stream`)을 버퍼링할 수 있다고 의심했으나, **실측 결과 버그가 아니다.**

- `starlette 0.41.3` 소스(`middleware/base.py:168-225`) 확인: `BaseHTTPMiddleware`는 `_StreamingResponse` + `body_stream()`으로 **청크를 도착 즉시 전송**한다(전체 바디를 먼저 읽는 구형 버그는 이미 패치됨).
- **실측(실제 TCP, uvicorn + httpx)**: 5청크 × 0.3s 지연 생성 엔드포인트에 대해
  - 미들웨어 **없음**: 도착 시각 `[0.43, 0.74, 1.06, 1.36, 1.67]`
  - 미들웨어 **있음**: 도착 시각 `[0.38, 0.69, 0.99, 1.3, 1.6]`
  - → 둘 다 0.3s 간격으로 청크 도착 = **스트리밍 정상**. (최초 테스트에서 TTFB=1.5s가 나온 것은 httpx `ASGITransport` 인프로세스 클라이언트의 버퍼링 아티팩트였음 — 서버 측 문제 아님)

→ **오판 정정.** 따라서 이 항목은 "수정 필요 버그"에서 제외한다. (참고: 미들웨어는 요청마다 작업 그룹+메모리 큐를 거쳐 미세한 오버헤드가 있으나, 스트리밍/BLK 기능에는 영향 없음 → 선택적 최적화 P2)

### 2.3 🔴 회원가입 플로우 토큰 미발급 (실재 에러 버그) — **수정 대상 P0**

**증상**: 모바일에서 회원가입하면 앱이 "이메일 인증 링크를 확인하세요"라고 띄우고 **로그인되지 않은 채로 종료**된다. 사용자는 막힌다.

**원인(코드 근거)**:
- `backend/app/api/auth.py:343-351` — `signup`이 **무조건** `token=""`(미발급) + `email_verification_required=True` 를 하드코딩.
- `backend/app/api/auth.py:41-49` — `_email_verify_enforced()` = `require_email_verification AND email_mode=="smtp"`.
- 현재 설정: `require_email_verification=True` **이지만** `email_mode='console'`(콘솔) → `_email_verify_enforced()` = **False**.
  - 즉 이메일 인증은 **실제로 강제되지 않고**, 콘솔 모드에선 **메일도 발송되지 않는다**(로그만 남음).
  - `login`(388행)도 강제 안 함 → 자격증명으로는 로그인 가능.
- 모바일: `mobile/screens/index.js:1518-1524` — `result.email_verification_required` 가 참이면 "이메일을 확인하세요" 출력 후 **return(로그인 안 함)**.
- 결과: 가입 시 토큰이 `""`이고 플래그가 `true` → 모바일은 메일 확인 안내만 보이고 로그인되지 않음. **그런데 메일은 오지 않음** → 사용자 영구 스톡.

**확인(실행)**: `config` 값 `require_email_verification=True / email_mode=console` 실측 확인. E2E `TestClient` 가입 응답에도 `token` 필드가 비어 있음.

## 3. 수정 기획 (Fix Plan)

### P0 — 회원가입 플로우 토큰 발급 (기능 블로커, 즉시 수정 권장)

**파일**: `backend/app/api/auth.py` (signup 핸들러, ~343-351행)

**수정 방향**: 인증 **강제 여부에 따라 동작을 일치**시킨다.
- 강제 안 됨(console 모드 등) → 토큰 발급 + `email_verification_required=False` → 모바일이 바로 로그인.
- 강제 됨(smtp 모드) → 토큰 미발급 + `email_verification_required=True` → 기존 이메일 인증 흐름 유지.

```python
# auth.py signup 응답 부분 (의사코드)
enforced = _email_verify_enforced()
token = _make_token(sub_id) if not enforced else ""
...
return AuthResponse(
    sub_id=sub_id,
    token=token,
    ...
    email_verification_required=enforced,
)
```
단, `email_mode='console'` 에서도 "인증 메일 발송" 호출(`auth.py:339`)은 무의미하므로 `enforced` 일 때만 발송하도록 가드.

**검증**: `TestClient` 가입 → console 모드에서 `token`非空 + `email_verification_required=False` 단언. 모바일 가입 플로우가 `AppState.login` 으로 진입하는지 확인.

### P1 — (선택) 미들웨어를 순수 ASGI 로 전환 (처리량 미세 최적화)

`BaseHTTPMiddleware` 는 요청마다 task-group + in-memory stream 을 거쳐 미세 오버헤드가 있다. 스트리밍 정상엔 영향 없으나, 고처리량이 필요하면 `RateLimitMiddleware`/`RequestIDMiddleware` 를 순수 ASGI 미들웨어(`def __call__(self, scope, receive, send)`)로 재작성. **기능 버그는 아니므로 우선순위 낮음.**

### P2 — E2E 커버리지 보강 (회귀 방지)

- 회원가입→자동로그인 풀 플로우를 `TestClient` E2E 스크립트(`scripts_bugtest_e2e.py`)에 추가.
- `/chat/stream` 실 LLM 호출 스모크 테스트(현재는 비스트리밍 `/chat` + 어노테이션/히스토리만 검증).

### P3 — 인프라 블로커 (코드 수정 불가, 운영값 필요 — 사용자 결정 대기)

| 항목 | 현재 | 영향 | 필요값 |
|------|------|------|--------|
| APK API 도메인 | `.env.mobile` 에 `127.0.0.1:8000` 하드코딩 | APK 설치 후 백엔드 연결 불가 | 운영 API URL |
| `PORTONE_CHANNEL_KEY` | 비어 있음 | 결제 요청 시 503 | PortOne 채널 키 |

→ 이 두 항목은 **임의로 값을 만들 수 없으므로** 사용자 제공/운영 설정 필요. 코드 측 대응(빌드 시 환경주입)만 제안 가능.

## 4. 정직 고지 (할루시네이션 방지)

- 성능 9건 수정, 버튼 배선, 어노테이션 동기화는 **코드를 직접 읽어 확인**했고, 스트리밍/회원가입/어노테이션 항목은 **실제 실행/실측**으로 검증했다.
- "스트리밍 버퍼링 버그" 의심은 **실측으로 버그 아님을 입증**해 정정했다(초기 httpx 인프로세스 아티팩트를 버그로 오인하지 않도록 함).
- 현재까지 **치명적 에러 버그는 1건(회원가입)** 발견. 나머지는 정상 동작 확인. 자동 버튼 audit 결과는 별도 반영.
