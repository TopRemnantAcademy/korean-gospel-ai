## 2. P0 — 즉시 개선 (가장 큰 병목)

### 2.1 백엔드 트레이서를 비동기/백그라운드 쓰기로 전환
- **문제**: `tracing.py:_emit()` 가 매 호출마다 `RotatingFileHandler.info()`(블로킹 디스크 I/O + 핸들러 락) + 재귀 `_scrub()` + `json.dumps()` 를 **이벤트 루프 내**에서 실행. `chat.py` 한 요청에 ~22회 trace 호출 → `CHAT_MAX_CONCURRENCY=8` 시 8개 채팅이 trace 쓰기 behind로 직렬화. 기본 설정(Langfuse 키 공백)에선 항상 로컬 JSONL 라이터가 살아 있어 운영 기본경로가 이 병목임.
- **접근**:
  1. `logging.handlers.QueueHandler` + `QueueListener`(또는 `ThreadPoolExecutor`)로 교체 — `_emit`은 큐에만 enqueue.
  2. 실제 파일 쓰기 + `_scrub` + `json.dumps` 는 리스너/워커 스레드에서 수행 (이벤트 루프 점유 0).
  3. 핫 경로엔 가벼운 span(`trace_start`, `generation` 시작/종료)만 emit하고 상세 이벤트는 샘플링.
- **영향 파일**: `backend/app/services/tracing.py` (리스너 도입), `backend/app/main.py` (리스너 shutdown 훅).
- **예상 효과**: 채팅 p99 지연 가시적 감소, 동시성 한계 완화.
- **리스크**: 낮음. 큐 크기 상한 + drop 정책으로 OOM 방지.

### 2.2 `/admin/activity/summary` 를 SQL 집계로 (메모리 50k 행 제거 + 정확성 버그)
- **문제**: `events.py:172-179` 가 최대 5만 ORM 행(`payload` JSON 포함)을 메모리에 materialize 후 Python에서 DAU/WAU/MAU·Top 미디어·인기검색 집계. **정확성 버그 포함**: `order_by(desc).limit(50000)` 이라 윈도우 내 이벤트가 5만을 넘으면 DAU/MAU/Top가 무 silently undercount. 또한 **쓰기 세션**(`get_session()`)을 점유해 채팅 쓰기와 경합.
- **접근**:
  1. DAU/WAU/MAU: `func.count(func.distinct(coalesce(subscriber_id,'d:'||device_id)))` 를 `date(created_at)` 기준 `group_by` (또는 1/7/30일 고정 버킷 `CASE` 카운트).
  2. `events_by_type`: `group_by(event_type)` + `func.count()`.
  3. `top_media`/`top_search`: `media_id`/`query` 를 **실제 인덱스 컬럼으로 승격**(현재 JSON payload에 묻힘) → `group_by` + `order_by(count).limit(20)`.
  4. `get_session()` → `get_read_session()` 으로 전환, `limit(50000)` 제거.
- **영향 파일**: `backend/app/api/events.py` (요약 쿼리 재작성), `backend/app/models/orm.py` (`ActivityEvent` 에 `media_id`/`query` 컬럼 추가 + 인덱스).
- **예상 효과**: 메모리 사용량 수십 MB→수 KB, 응답시간 수 초→수십 ms, 집계 정확도 복원.
- **리스크**: 중간. 스키마 컬럼 추가(신규 컬럼이라 드리프트 위험 거의 없음) + 마이그레이션/인제스트 시 기존 payload에서 컬럼 채우기.

### 2.3 모바일 — 부분 상태변경 시 전체 화면 재렌더 차단
- **문제**: 모든 탭 전환이 `AppState.on('activeTab') → renderScreen() → empty(container) + 전체 DOM 재구축` 구조(뷰 캐시/keep-alive 없음). 작은 토글에도 전체 스크린이 다시 그려짐.
  - **찬양 즐겨찾기 토글** → `renderHymns()` 전체 재실행 (`screens/index.js:321`). 100~수백 트랙 재생성 + 카드별 `hymnFavorites.includes()` O(n²).
  - **성경 장/권 변경** → `renderBible()` 전체 재실행 (`screens/index.js:75/100/104`). 매 페이지 넘김마다 `getBooks()`(`meta.json` 미캐싱) 재읽기 + 장 전체 절 노드 재구축.
- **접근**:
  - 즐겨찾기 토글은 해당 아이콘 1개의 class/text만 패치 (`screens/index.js:619-622` 설교 fav 패턴 차용). `renderHymns()` 호출 제거.
  - 성경은 컨트롤은 유지한 채 `passageEl` 만 `empty()` 후 `renderPassage()` 로 교체. `getBooks()` 결과 캐싱.
- **영향 파일**: `mobile/screens/index.js`.
- **예상 효과**: 저사양 안드로이드에서 탭/페이지 넘김 jank 대폭 감소.
- **리스크**: 낮음. 서브트리 갱신으로 범위 한정.

## 3. P1 — 높은 임팩트

### 3.1 관리자 — 5개 데이터 페이지 `@st.cache_data` 도입
- **문제**: `21/20/9/5/4` 페이지가 매 rerun마다 백엔드 중량 엔드포인트를 **캐시 없이** 동기 호출(`api_client.py` httpx `timeout=60~180s`). 캐싱은 `15_📥_자료흐름.py` 뿐. 슬라이더/라디오 1회 클릭에 전부 재실행.
- **접근**: 각 fetch 함수를 `@st.cache_data(ttl=30~60, show_spinner=False)` 로 래핑(파라미터 키). 명시적 write 액션 시에만 `cache_data.clear()`.
- **영향 파일**: `admin/pages/21_📡_활동모니터링.py`, `20_📊_백데이터분석.py`, `9_👥_유저관리.py`, `5_💭_대화기록.py`, `4_📊_Status.py`.
- **예상 효과**: 대부분의 중복 로드 즉시 제거.
- **리스크**: 낮음. TTL 내 데이터 약간 늦게 반영(의도된 것).

### 3.2 백엔드 — 멀티워커 공유 캐시 (Redis)
- **문제**: `faq_cache._cache`, `answer_cache._mem`, `embedding/factory._QUERY_CACHE` 등이 모두 **프로세스 로컬**. `--workers N`/gunicorn 시 워커마다 개별 워밍업 → 핫 쿼리 콜드 미스·중복 임베딩/LLM. `config.redis_url` 기본 `None` 이고 `faq_cache` 는 Redis 경로 자체 없음.
- **접근**: `redis_url` 설정 시 `faq_cache`·임베딩 쿼리 캐시를 Redis(TTL)로 백업해 워커 공유. 동일 쿼리가 빈번하므로 임베딩 캐시 공유가 단일 최대 반복연산 절감.
- **영향 파일**: `backend/app/services/faq_cache.py`, `embedding/factory.py`, `config.py`(`redis_url` 사용), `main.py`(redis 풀).
- **예상 효과**: 워커 확장 시 처리량 선형 향상, 메모리 중복 감소.
- **리스크**: 중간. Redis 의존성 추가(환경에 없으면 프로세스 로컬 폴백 유지).

### 3.3 모바일 — 슬립타이머/포그라운드 전체 재렌더 제거
- **문제**:
  - 슬립타이머 활성 시 `setInterval(1000)` 이 `'sleep'` emit → 리스너가 `renderSheet()` 전체(가사/요약 DOM) 재구축 (초당 1회, `player.js:460-463,740,925`).
  - 포그라운드 복귀 시 `MediaService.invalidate()` + `renderScreen()` 으로 전체 카탈로그 네트워크 재페치 + 전체 재렌더 (`app.js:355-356`).
- **접근**:
  - 카운트다운 배지만 별도 엘리먼트로 분리해 `textContent`/class 1회 갱신(가사 재구축 금지).
  - 포그라운드 무조건 invalidate 대신 `MediaService.list` 의 version 체크 결과로 실제 변경 시에만 재렌더.
- **영향 파일**: `mobile/player.js`, `mobile/app.js`.
- **예상 효과**: 슬립 중 UI freeze 제거, 앱 전환 시 불필요한 재다운로드 제거.
- **리스크**: 낮음.

## 4. P2 — 중간 임팩트

### 4.1 모바일 — 진행률/채팅 스트리밍 reflow 제거
- **문제**:
  - `player.js:updateProgress` 가 스타일 쓰기 후 `offsetTop`/`clientHeight`/`scrollTop` 읽기 → 틱(초당 ~4회)마다 강제 동기 레이아웃.
  - 채팅 스트리밍이 토큰마다 `textContent` + `scrollTop = scrollHeight` → 토큰당 reflow(수백 회/응답).
- **접근**: DOM 읽기/쓰기 배치(먼저 지오메트리 읽기 → 쓰기), 또는 활성 인덱스 변경 시에만 `scrollTop` 갱신. 채팅은 `requestAnimationFrame` 으로 스크롤을 프레임당 1회로 throttle(또는 마지막 토큰만).
- **영향 파일**: `mobile/player.js`, `mobile/screens/index.js`(채팅 스트림 콜백 `:1349`, `addMessage` `:1427`).
- **리스크**: 낮음.

### 4.2 관리자 — 탭 지연로딩 + 이벤트 테이블 페이지네이션
- **문제**:
  - `4_📊_Status.py` 가 rerun마다 3탭 fetch를 무조건 전부 실행(탭 1개 봐도 ~7회 호출).
  - `5_💭_대화기록.py` 가 최대 200개 대화를 expander(전문+위젯 3~4개)로 일괄 렌더(페이지네이션 없음).
  - 활동 이벤트 테이블은 500건 캡이지만 `offset` 미사용 → 그 이상 미탐색.
  - `list_subscribers` 는 200건 silent cap + offset 미전달.
- **접근**:
  - `Status.py` 탭을 활성 탭 기준 지연로딩(또는 `@st.cache_data`).
  - 대화기록/이벤트/유저를 페이지 단위(20~50행 + "이전/다음" 또는 `st.dataframe` 행선택→상세)로 분할.
- **영향 파일**: `admin/pages/4_📊_Status.py`, `5_💭_대화기록.py`, `21_📡_활동모니터링.py`, `9_👥_유저관리.py`, `backend/app/api/*`(offset/limit 지원 확인).
- **리스크**: 낮음~중간(페이지 UI 재설계 약간).

### 4.3 백엔드 — 다국어 임베더/reranker 워밍업
- **문제**: `embedding/factory.get_embedder("bge_m3")` 가 첫 다국어(en/zh/ja) 요청에 늦게(lazy) ~1GB 모델 로드(`main.py` 는 기본 kure만 프리웜). 첫 다국어 채팅이 수 초 스톨. `reranker` 기본값 `"none"`(CrossEncoder 실제 미동작) — 켜면 ~1.1GB + 매 요청 CPU.
- **접근**: `lifespan._warmup_models` 에서 `rag_bilingual_enabled` 게이트로 bge_m3 임베더(및 reranker=bge_m3 시 reranker)도 프리웜. reranker는 `rerank_top_n` 소집합만 처리하도록 명시적 결정.
- **영향 파일**: `backend/app/main.py`, `embedding/factory.py`, `config.py`.
- **리스크**: 중간(메모리 점유 증가 — 8GB 박스 시 `RERANKER_MIN_FREE_MEM_BYTES` 가드 고려).

## 6. 이미 건강 — 손대지 말 것 (오탐 방지)

- 임베딩/스파스/Qdrant/reranker 추론은 이미 `asyncio.to_thread` 로 오프로드.
- 임베딩/reranker/LLM/Qdrant/스파스 인코더는 모두 싱글톤(모듈 import 시 1회 로드).
- DB 쓰기는 `to_thread` 래핑, 읽기/쓰기 풀 분리됨. `ActivityEvent`/`Interaction` 인덱스 존재.
- `EventService` flush 는 `keepalive` 비동기, 버퍼 상한(600) 있어 누수 없음.
- `AppState.on`/`Player.on` 구독 누수 없음(부트 시 1회, 설교 스크린은 unsub 처리).
- 렌더 경로에 블로킹 IndexedDB/localStorage 쓰기 없음(`chatMessages`만 동기 저장, 제스처 시점).
- 활동 이벤트 테이블은 500건 캡(무한 dataframe 아님). 날짜 필터는 이벤트 조회에 이미 전달됨.

## 7. 권장 구현 순서

1. **P0**: 2.1 트레이서 비동기 → 2.2 summary SQL 집계(스키마 컬럼 추가 포함) → 2.3 모바일 부분 렌더.
2. **P1**: 3.1 관리자 캐시 → 3.3 모바일 슬립/포그라운드 → 3.2 Redis 공유 캐시.
3. **P2**: 4.1 reflow → 4.2 관리자 페이지네이션/지연로딩 → 4.3 다국어 워밍업.
4. **P3**: 위 표의 빠른 승리 항목들(검증 후 일괄).

> 각 단계 끝마다 **E2E/부하 검증** 권장: 백엔드는 기존 `scripts_test_events_e2e.py` 패턴 재활용 + `wrk`/간이 동시요청 테스트, 모바일은 저사양 기준 Puppeteer 뷰포트/ reflow 체크, 관리자는 `st.cache_data` 적용 후 rerun 횟수 측정.
