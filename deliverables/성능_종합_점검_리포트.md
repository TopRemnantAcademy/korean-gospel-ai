## 🔴 높음 — 동시 처리량 병목 (락/직렬화)

### 1. 임베딩 락 직렬화 (가장 큰 병목)
- **위치**: `backend/app/services/embedding/factory.py:135-144, 188-210`
- **증상**: `CachedEmbedder.embed_query`/`embed_documents`가 `with self._lock:` 블록 **내부에서** 실제 모델 추론(`self._inner.embed_query`/`embed_documents`)을 실행합니다.
- **원인**: 락이 "캐시 동시 접근 보호"용인데, CPU/GPU를 수백 ms 쓰는 KURE/BGE 추론을 통째로 잠급니다.
- **영향**: `retriever.py:262`가 `asyncio.to_thread`로 다중 확장쿼리 임베딩을 "병렬" 실행하지만, 쓰레드들이 이 단일 락에서 전부 직렬화 → 병렬화 무력화. 동시 채팅 사용자 N명의 캐시미스 임베딩이 N배로 늘어남.
- **근거**: 코드 읽기로 확인. 임베더는 `.env` `EMBEDDER=kure` (활성).

### 2. SQLite 쓰기 락 직렬화 (모든 채팅 요청)
- **위치**: `backend/app/services/token_service.py:96,138,167,192,221,307` — 전부 `get_session_immediate()`(=`BEGIN IMMEDIATE`) 사용
- **증상**: 모든 채팅 요청이 종료 시점에 `save_interaction_and_finalize_tokens`(chat.py:191,298,347,555,735,877,1108)로 **상호작용 저장 + 토큰 소비** 2건의 쓰기 트랜잭션을 실행.
- **원인**: SQLite는 단일 쓰기자만 허용(WAL). `BEGIN IMMEDIATE`가 쓰기락을 선점하므로 동시 채팅 N명의 쓰기가 **전부 직렬화**.
- **영향**: 요청당 쓰기 구간은 짧지만, 동시 사용자가 늘면 SQLite 쓰기가 처리량 상한이 됨. DB는 `sqlite:///.gospel.db` 기본(`db.py:50`, `DATABASE_URL` 미설정).

### 3. async 핸들러 내 sync DB 쿼리 (이벤트 루프 블로킹)
- **위치**: `backend/app/api/chat.py:400-401, 780-781`
- **증상**: `_chat_inner`(async, 168행)·`chat_stream`(async, 687행) 안에서 `with get_session() as _qs: _qs.query(Subscriber)...first()` 를 `to_thread` 없이 **인라인** 실행.
- **원인**: sync SQLAlchemy 세션(비동기 엔진 없음)을 async 핸들러에서 직접 호출.
- **영향**: SQLite 파일 I/O 동안 이벤트 루프 전체가 블로킹 → 해당 순간 **모든** 동시 요청이 지연. (동일 파일에서 `to_thread`로 우회하는 곳도 있어 불일치 — chat.py:509,784,1055는 `to_thread` 사용.)

## 🟠 중간 — 요청당 지연

### 4. BgeReranker 캐시 무효 + 스레드 안전성 결여
- **위치**: `backend/app/services/reranker.py:33, 27-45`
- **증상**: 캐시 키가 `(query, tuple(docs))` — **전체 문서 목록(순서 포함)**을 키로 사용. 검색 결과 목록은 요청마다 달라지므로 **사실상 항상 미스** → CrossEncoder 추론을 매 요청 실행(~50-200ms).
- **원인 2**: `self._cache`(OrderedDict)를 락 없이 변이. `retriever.py:327`이 `to_thread`로 호출하므로 다중 쓰레드 동시 변이 위험.
- **근거**: `.env` `RERANKER=bge_m3` (활성, config 기본값 `none`을 오버라이드). 단 1.5GB 여유 메모리 가드(101행)로 NoOp 폴백 가능성 있음.

### 5. Streamlit `httpx.Client` 매 호출 생성
- **위치**: `app.py:257,266,427,503,526,597,664,692`
- **증상**: 백엔드 호출마다 `with httpx.Client(timeout=...)`로 **새 클라이언트(=새 커넥션 풀)** 생성 → 매번 TCP+TLS 핸드셰이크(~50-150ms) 재수행.
- **원인 2**: `@st.cache_data`/`@st.cache_resource`가 **한 곳도 없음** → `_fetch_quota`(246행)도 rerun마다 재조회(438행).
- **영향**: Streamlit rerun(채팅 전송·버튼 클릭마다 발생)에서 불필요한 네트워크 핸드셰이크 누적.

## 🟡 중간-낮음 — 코퍼스/부하 확장 시

### 6. BM25 O(N) 선형 스캔 + 락 직렬화
- **위치**: `backend/app/services/sparse_index.py:126-143`
- **증상**: `search()`가 락을 잡은 채로 ① Kiwi 형태소 토크나이즈 ② `get_scores`(O(N) 전 코퍼스 스캔) ③ `sorted(전체)[:top_k]`(O(N log N) 정렬)을 수행.
- **실측**(1만 문서·문서당 20토큰 합성 코퍼스):
  - `get_scores`: **14.0ms** (지배적, 라이브러리 구조상 O(N))
  - 전체 정렬: 4.7ms → `heapq.nlargest`로 3.3ms (**1.4x**, 부차적)
- **영향**: 정렬보다 `get_scores`의 O(N) 스캔이 본질 병목이며, 이 전체가 락 안에서 실행 → 동시 검색 직렬화. **현재는 코퍼스가 작아(메인 `gospel_kure` 컬렉션 미존재) 저영향이지만, 인제스트 후 문서 수에 비례해 악화**하는 구조적 문제.

### 7. FAQ 캐시 무한 성장 + 질문어 제거(정합성)
- **위치**: `backend/app/services/faq_cache.py:55, 42-45`
- **증상**: `_cache` 딕셔너리에 **크기 상한이 없고** TTL(24h, `faq_cache_ttl_sec=86400`) 만료만 존재. 다양한 질문 트래픽에서 24시간 창 내 무한 성장.
- **부수 정합성**: `_normalize_query`가 `왜|어떻게|무엇|뭐|언제|어디` 등 **의문사를 제거** → "왜 기도해야 하나요"와 "기도해야 하나요"가 동일 키로 충돌, 잘못된 캐시 답변 서빙 가능(성능은 아니나 품질 이슈).

### 8. `_sparse_cache` 스레드 안전성 결여
- **위치**: `backend/app/services/vector_store.py:301-318`
- **증상**: `_to_sparse`의 dict 변이(캐시 조회/삽입/축소)가 락 없음. `to_thread`(retriever)로 동시 호출 → dict 동시 변이 위험.
- **부수**: 축소 시 `list(keys())[:max//2]`로 O(N) 복사(312-316행).

## 영향 우선순위 (개선 권장 순서)

1. **#1 임베딩 락 제거** — 추론을 락 밖으로 이동(DCL 유지), 모델 스레드 안전성 확인 후. 동시 처리량에 가장 큼.
2. **#2+#3 DB 쓰기/읽기 병목** — Postgres 전환(pooling+async) 또는 최소한 sync 쿼리 `to_thread` 일괄 적용. `BEGIN IMMEDIATE` 쓰기 경로 재설계(배치/지연 기록).
3. **#4 Reranker 캐시 재설계** — `(query,)` 단위 캐시 + 락 추가, 또는 RRF만 쓰도록 기본 전환.
4. **#5 Streamlit 커넥션 풀** — `st.cache_resource`로 httpx.Client 싱글턴화.
5. **#6 BM25** — 코퍼스 확장 전 inverted-index 또는 `heapq.nlargest`(부차) + 락 범위 축소.
6. **#7 FAQ 캐시** — 크기 상한(LRU) + 의문사 보존 정규화.
